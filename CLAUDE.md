# Monitoring System — Error Tracking SDK

## What we're building
An in-house error tracking SDK, similar to Bugsnag or Sentry but owned entirely by the company. It's original code: never wrap or import Sentry, Bugsnag, Crashlytics, etc. The SDK runs inside client apps, watches for errors, performance problems, memory issues and crashes, and POSTs JSON events to a backend endpoint.
The original spec scoped this to client SDKs only. On 2026-10-17 the user added a **backend + dashboard** (`project/backend/`), merged on 2026-10-30 into one Next.js app, `project/web/` (see below).

Three SDKs, all sending the **same shared payload schema**:
| SDK | Path | Stack | Status |
| --- | --- | --- | --- |
| JS | `error-tracking-sdk/js/` | TypeScript → ES5, Rollup (ESM + CJS), Vitest, zero runtime deps | ✅ Done (2026-10-17) |
| iOS | `error-tracking-sdk/ios/` | Swift 5.5+, iOS 14+, Swift Package + Podspec, XCTest | ⏳ Not started |
| Android | `error-tracking-sdk/android/` | Kotlin 1.8+, API 21+, Gradle AAR, JUnit4 + Mockito | ⏳ Not started |

**Full original spec (requirements for every SDK, shared schema, test scenarios): [docs/SPEC.md](docs/SPEC.md).** Read it before starting iOS, Android or the test-scenario suite.

## Core rules (from the spec)
- **The SDK must never crash the host app.** Every SDK failure fails silently, with at most a debug log.
- No console, Logcat or NSLog output unless `debug: true`.
- The API key exists only in memory and in the outgoing request header. Never persist it.
- Every schema field is always present. Use `null` when a platform can't provide it; never omit a field.
- No `any` in TypeScript. No `!` force-unwraps in Swift or Kotlin without a comment. Doc comments on every public method.
- No magic numbers: all thresholds go in a constants file.
- No third-party packages unless the spec lists them. Ask first.
- Ask the user before choosing between two implementation approaches.
- **No screen capture of any kind** (screenshots, screen recordings, view snapshots) in any SDK: security requirement. Events carry only the schema fields; anything else is dropped (JS `withField`, backend `server/validate.ts`).
- Build order: types → core queue and payload builder → transport and retry → collectors → public API → tests → README.

## Decisions already made (keep all 3 platforms consistent)
- **Batch body:** `{ "events": [ ... ] }`. Headers: `Content-Type: application/json` and `X-API-Key`.
- **Retry:** network errors, 5xx, 408 and 429 are retried 3× (1s/2s/4s). Other 4xx responses are dropped with no retry.
- **Error-storm protection:** identical events (type + message + top frame) are deduplicated within 5 s, then a rate limit of 100 events per rolling minute applies.
- **Extra JS fields beyond the shared schema:** `level`, `context`, `performance.cls`, `device.referrer`. ⚠️ Still needs backend sign-off. iOS and Android should probably include `level` and `context` too.
- **Performance events:** `event_type: "performance"`, with the issue in `error.type` (`SlowPageLoad`, `SlowApiCall`, `MemoryLeakSuspected`, `MainThreadBlocked`, `LowFrameRate`) and `handled: true`.
- **Error types built by the SDK** (all `event_type: "error"`): `HttpError`, `NetworkError`, `InvalidJsonResponse`, `ResourceError`, `CspViolation`, `WorkerError`, `ConsoleError`, `CrossOriginScriptError`, `PageNotFound`. Extra detail goes in `context`.
- **`PageNotFound` (2026-10-19, JS 0.3.0):** `collectors/pageNotFoundCollector.ts` reads the document's Navigation Timing `responseStatus` once at install; 404/410 → event with level `warning`, `handled: true`, empty stack, message `Page not found: <path>`, context `{ url, path, status, referrer, source: 'http-status'|'app' }`. Public `capturePageNotFound(url?)` covers SPA route misses and Safari; same message + empty stack so the client dedup collapses a manual call on an auto-detected 404. Config `detectPageNotFound` (default true). Backend groups one issue per path. Verified in headless Chrome + local backend + dashboard.
- **`screen` field + `setScreen()` (2026-10-28, JS 0.8.0, user chose "option B"):** Appzillon changes screens on one URL, so `device.url` said nothing. New top-level schema field `screen: string | null` on every event (shared schema, not a JS extension; I picked top-level over `context.screen`, user hadn't objected). `setScreen(name|null)`: trimmed, cut to `MAX_SCREEN_NAME_LENGTH` (200), non-strings ignored, repeats ignored; leaves a `navigation` breadcrumb `Screen: X` and starts a new page view (`PageViewCollector.onScreenChange`); each view remembers its own screen so a view ended by a screen change is sent with the old one, and a view with no screen yet just takes the first name (so the page-load vitals belong to the app's first screen). Event list on the issue page shows each event's screen. Verified 2026-10-28: 235 SDK tests, 106 backend tests (in-memory MongoDB), and an e2e run in headless Chrome (built SDK → dev-server → API + dashboard, 16/16 checks, both themes, 390 px) via a scratchpad script. Backend: `validate.js` keeps it, events/transactions store `screen`, `pageRouteOf()` groups page views by screen else normalized route, issue page's "Page" row shows `screen · url` (user asked: the URL alone looked wrong on Appzillon), insights "Screen" fact prefers it. Appzillon snippet should call `ErrorTracker.setScreen(...)` in its `apz.launchScreen` / `launchSubScreen` wrapper. SPEC + PROTOCOL updated.
- **API call `_id` (2026-10-28, JS 0.9.0; user's manager asked for a "traceID" per API call, user chose a plain unique `_id` to find the call in the DB, not tracing):** `core/ids.ts` `randomRequestId()` = 16 lowercase hex (`REQUEST_ID_BYTES` 8, `crypto.getRandomValues`, `Math.random` fallback), created once in `NetworkInterceptor.emit()`; the same id goes into `api_calls`/`slow_api_calls`, the `api` breadcrumb `data._id`, the transaction span and `context._id` of HttpError/NetworkError/SlowApiCall. **Not** sent as a request header (no CORS/app risk; could be added later for server-log correlation). Not on `InvalidJsonResponse` (it patches `Response.json`, which has no link to the call). Backend: `validate.js` `requestId()` keeps strings ≤ `MAX_REQUEST_ID_LENGTH` (64) else null; indexes `events.payload.performance.api_calls._id` and `transactions.spans._id`; `GET /api/issues?q=<_id>` also matches issues whose events recorded that call and returns `matchedEventId`, so the dashboard row opens that exact event; issue page "API calls" lines start with the id; endpoint "Slowest calls" has a "Call id" column. Verified 2026-10-28: 240 SDK tests, 111 backend tests (local mongod), and a real-Chrome e2e (built SDK page with fetch + Appzillon-style XHR → dev-server → Mongo lookups with positional projection + IXSCAN → dashboard search/issue/endpoint pages, 24/24, both themes, 390 px). Project hints in `public/insights.js` skip `context._id` (a hint "500" must not match a random id). SPEC + PROTOCOL updated.
- **`BlankPage` (2026-10-29, JS 0.10.0; user: "page suddenly goes white, why?"; user chose point sampling, DOM-change + error triggers, on by default, separate linked event):** `collectors/blankPageCollector.ts`. `samplePage(hint)` hit-tests (`elementsFromPoint`, ~0.33 ms each on a 9k-node page, the only real cost) cheapest first: the element seen last time (`lastSeen`), then in-viewport content elements in DOM order (≥2 px so sr-only text doesn't count, max 50, stops after 10 covered), then 17 points on the centre lines (background images, open shadow roots). Looks through transparent layers; an opaque empty layer = "covered"; `pointer-events:none` content counts (element visible and nothing opaque on top), `visibility:hidden`/`opacity:0` don't. Production review 2026-10-29 fixed: pointer-events/shadow-DOM/sr-only cases, in-flight counter leaks (XHR re-`open()` while running, fetch throwing synchronously), skip sampling already-reported screens, stop the observer after max reports. Measured in real Chrome: ~0.5 ms per check on a 9k-node page (was 19 ms), ~17 ms on a really covered page; dialog on a white backdrop and small corner dialogs are not blank. Checks: after load, `setScreen`/route change (resets the blank timer), uncaught error, and a MutationObserver (quiet 1 s, max 5 s); must stay blank 2 s (up to 10 s while `NetworkInterceptor.pendingRequests()` > 0, new in-flight counter); once per screen key (screen else path), max 5/page; hidden tab → re-check when shown. Cause (10 s window, first match): page_http_error, resource_failed, code_load_failed (chunk/import regex), csp_blocked, js_error (uncaught or `captureError`), session_expired (401, seen via the interceptor even though 401 isn't an HttpError), api_failed, api_pending, main_thread_blocked, covered_by_overlay, nothing_rendered. Event: `event_type: error`, type `BlankPage`, `handled: false`, fixed message per cause (one issue per cause), context with `error`/`request` (`_id`). Constants `BLANK_PAGE_*`, option `detectBlankPage`. Demo: `project/web` `/blank` (5 scenarios, `api/profile`, `api/session`). Verified 2026-10-29: 274 SDK tests, and real headless Chrome against the demo's test build with a local capture server (scratchpad `blank-e2e.mjs`): no event on /, /products, /about, /blank; scenarios 1–5 → js_error, code_load_failed, nothing_rendered, session_expired, covered_by_overlay. Backend/dashboard: nothing special yet (stored as a normal issue). README + PROTOCOL updated.
- **HTTP error statuses (2026-10-23, JS 0.6.0, user chose option A):** `httpErrorStatuses` option (codes and inclusive `[min, max]` ranges); default `[400, 404, 405, 413, [500, 599]]` (`DEFAULT_HTTP_ERROR_STATUSES`), so 401/403/409/422/429 are no longer reported. Invalid entries are ignored, `[]` reports none. iOS/Android should use the same name and default.
- **0.6.1 fixes (2026-10-23, from reviewing real Appzillon / assistant app events):** `MainThreadBlocked` context `{ duration_ms, threshold_ms, started_at_ms, during_page_load }` and `LowFrameRate` context `{ fps, threshold_fps, during_page_load }` (during_page_load = before the load event ended); leak rule also needs each floor step ≥ `LEAK_MIN_STEP_MB` (0.5, scaled down to half the average step for slow-leak settings via `minLeakStepBytes`) and no step > `LEAK_MAX_STEP_SHARE` (70%) of the rise (a real false positive had floors [13.3, 13.3, 13.3, 36.1] that crept by KB); clicks on `body`/`html` record no text. Backend Performance "Failed" uses `FAILED_HTTP_STATUSES` in `lib/constants.js` (= SDK default list; user chose: 401/403 aren't site problems), and slow-sample rows carry `failed`. Old rollups keep their old counts.
- **`handled` rule:** `false` = broke without app code getting a chance (uncaught exceptions/rejections, failed resources, CSP, workers). `true` = handed back to the app (HTTP status, rejected request, JSON parse error, console.error, perf issues, `captureError`).
- **One failure, one event:** `core/reportedErrors.ts` remembers reported error objects (WeakSet) and short-lived text signatures, so the same failure arriving by a second route (unhandledrejection, console.error, worker error re-dispatched on window) is skipped.
- **Error storms:** when the rate limit drops events, one `EventsDropped` message (`context.dropped_count`) is sent 10 s later.
- **User decisions (2026-10-17):** track server errors via Next.js `onRequestError`; freezes via the Long Tasks API only (no watchdog worker); `captureConsoleErrors` opt-in, default off; cross-origin "Script error." is documented and labelled, with no try/catch wrapping of browser APIs.
- URLs have their query string and fragment stripped before recording (PII).
- Offline / failed-delivery events are persisted (JS: `localStorage["_et_queue"]`, max 50, oldest halved away if storage is full).

## JS SDK on npm
- Package: **`@sourav732/error-tracker-js`**, public, from the user's own npm account. **0.1.0, 0.2.0, 0.3.0 and 0.3.1 are published** (plus a stray `0.0.0-stage`). **0.5.0** is published too (released 2026-10-23; includes the never-published 0.4.0 work: memory-leak detector rewrite, background-tab FCP/LCP fix; plus performance monitoring). 0.6.0, 0.6.1, 0.6.2 and **0.7.0** are published too (checked on npm 2026-10-27). **0.7.1** (XHR timing fix below) is published too (checked 2026-10-28); **0.8.0** (`setScreen`) is published too (checked 2026-10-28). **0.9.0** (API call `_id`) and **0.10.0** (`BlankPage`) are prepared locally and the user still has to publish them (`build` empties `dist/` first, so stale `.d.ts` files can't ship).
- **XHR timing (2026-10-27, 0.7.1):** XHRs are recorded at the first of `readystatechange` DONE / `load` / `error` / `abort` / `timeout` (listeners added in `open()`, `abort()` wrapped, timeout inferred from `xhr.timeout`), not at `loadend`. jQuery runs app callbacks on the earlier events, so errors reported from a request callback (e.g. the Appzillon snippet's `serverError`) used to miss the request that caused them. Only finishes at `readyState` DONE count (a late `loadend` after the app re-opens the XHR in `onload` is ignored), and `send()` only starts tracking on an OPENED, unsent XHR. Verified in real Chrome against the built SDK (9 checks: jQuery 1/2/3 styles, polling, abort, timeout, sync, double send); published 0.7.0 fails 4 of them. License stays `UNLICENSED`.
- **Memory-leak detection (2026-10-23, 0.4.0)**, after a false `MemoryLeakSuspected` (6.8 → 9.2 MB during login on an Appzillon app whose screens change without URL changes): 60 s warm-up → readings grouped in windows of 4 polls, each window's lowest reading = "floor" (≈ heap after GC) → leak only when the last `memoryLeakReadings` (default 4) floors each rise AND the newest floor is above the lowest floor seen by `memoryLeakGrowth` (20%) AND `memoryLeakMinGrowthMb` (new, default 10). No reset on navigation (SPA route leaks are the common case). One report per page, measurements in `context`. Real Chrome's `performance.memory` was measured precise and live (not bucketed) in headless Chrome. `onPerformanceIssue` takes an optional `context`; `CollectorSink.onNavigation(url)` now feeds page views (not the memory collector).
- **Background tabs:** FCP/LCP are null if the page was hidden before them (web-vitals rule, incl. `visibility-state` entries from before init), and `SlowPageLoad` isn't reported if the page was hidden before `loadEventEnd`. `core/visibility.ts` (`VisibilityTracker`, hidden periods) is shared by performance + page views.
- **Performance monitoring ("Stage 2", 2026-10-23, 0.5.0), Sentry-style.** User decisions: per-request `SlowApiCall`/`SlowPageLoad` issues are **opt-in** (`captureSlowEvents`, default false; when on: duration in `context`, 5 min cooldown per endpoint); `performanceSampleRate` default **1.0** (decided once per page load, separate from `sampleRate`). `collectors/pageViewCollector.ts` sends one `event_type: "transaction"` per page view (`transaction` field, shared schema in docs/SPEC.md; `transaction: null` on all other events): route, kind pageload|navigation|continued, Web Vitals + INP (Event Timing), long tasks, ≤100 request spans with Resource Timing server/download/size (observer + `getEntriesByName` fallback; views ended by a route change wait 250 ms because Chrome adds entries ~60 ms late for unread bodies). Views end on route change, tab hidden, pagehide, or 30 min. Own client rate limit (30/min) and `beforeSendTransaction`. **Delivery fix:** same-tab navigation fires `pagehide` but no `visibilitychange`, so queued events were only persisted; now `EventQueue.sendBeforeUnload()` + `HttpTransport.sendOnUnload()` send them with `fetch keepalive` (≤60 KB, falls back to localStorage); keepalive is also used for sends while hidden, with a no-keepalive retry if the browser refuses it. Verified in headless Chrome (cross-origin + preflight keepalive works).
- **Configurable thresholds (2026-10-19, user chose flat options):** `init()` takes optional `slowApiCallMs`, `slowPageLoadMs`, `mainThreadBlockedMs`, `lowFrameRateFps`, `memoryPollIntervalMs`, `memoryLeakGrowth`, `memoryLeakReadings`. Defaults and min/max stay in `constants.ts`; `resolveConfig()` clamps out-of-range values and ignores non-numbers. Transport, rate-limit and dedup limits are deliberately **not** configurable. iOS/Android should offer the same option names.
- `prepublishOnly` runs typecheck + tests + build, so `npm publish` can't ship a broken build. The build is minified with `@rollup/plugin-terser` (ES5, ~67 KB per format, with source maps).
- `SDK_VERSION` in `src/constants.ts` must equal the `package.json` version; a test enforces it. Bump both together.
- The user runs `npm login` / `npm publish` themselves (needs their account and 2FA).
- Verified 2026-10-17: the `npm pack` tarball installed in a fresh project works via CJS, ESM and strict TS, with zero runtime deps, and `npm publish --dry-run` passes.

## JS SDK quick reference
```bash
cd error-tracking-sdk/js
npm run typecheck   # strict TS over src + tests
npm test            # Vitest + jsdom (274 tests passing)
npm run build       # dist/index.mjs, dist/index.cjs, dist/types
```
- `src/core/client.ts` drives the pipeline: sample → dedup → rate-limit → build → beforeSend → queue.
- `src/core/eventQueue.ts`: batching, retry, offline persistence. `src/transport/`: fetch sender and localStorage store.
- `src/collectors/`: error, breadcrumb (+ opt-in console errors), blankPage, performance, memory, httpError (HTTP + network failures), jsonResponse, responsiveness (long tasks + FPS), csp, worker, resource (fonts, CSS images, pre-init failures), pageView (transaction events). `networkInterceptor.ts` is the single fetch/XHR wrap they share; it also passes the failure kind and the app call-site stack.
- Automatic collectors only install when `window` exists; in Node the SDK is used for `captureError` only (Next.js server errors).
- Vitest: don't use `vi.runAllTimersAsync()` with an initialised client, because the FPS sampler's repeating timer never ends. Use `advanceTimersByTimeAsync(ms)`.
- Schema shape test helper: `expectSchemaShape()` in `tests/helpers.ts`.
